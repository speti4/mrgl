# The CurseForge Core API: the key, the application and the terms

Verified: 2026-10-22, the outcome added 2026-10-29. The terms and the application route are CurseForge's (Overwolf's) to change; re-check
the sources before relying on a claim here. Task 007 is the application; the source implementation is M4.

## The key

The CurseForge Core API (`https://api.curseforge.com`, documented at https://docs.curseforge.com/rest-api/)
takes an API key on every request in the `x-api-key` header. There are two kinds of key:

- a **CurseForge for Studios** key, generated by a game developer in the developer console
  (https://console.curseforge.com/) for their own game's modding; and
- a **third-party application** key: "If you're running a 3rd party modding service, we have an API solution
  for you. Click here to apply for a key." The application is a form linked from the documentation's
  introduction, reviewed by the Overwolf team; on approval the key is generated and the developer is
  contacted by e-mail. The documentation warns that "any registered account which is not a game developer and
  did not request a key, will be deleted", so a console account exists only together with an application.

The upload tokens of `curseforge.com → Settings → My API Tokens` are a third thing: they upload files for an
author and read nothing.

Since the enforcement date named in CurseForge's post of 2026-06-10 (2026-07-16), a file download from the
CDN (`edge.forgecdn.net`) needs the key as well, in the `x-api-key` header (recommended) or as an `api-key`
query parameter; a request without one gets `401 Unauthorized`, "A valid api-key is required". So a manager
without a key cannot even download a file whose URL it knows.

## The application

The support article "About the CurseForge API and how to apply for a key" describes the form: contact
information, a project description, links, the expected API use, and the acceptance of the 3rd Party
Developers API Terms of Service. The reviewers weigh three things: the effect on the authors' earnings, the
effect on CurseForge's servers and CDN, and whether authors consent to the third-party distribution of their
creations. No review time is published. The history in
[the alternatives page](2026-10-21-addon-manager-alternatives.md#the-ajour-and-wowup-history) (WowUp's
application refused in 2022 after its partnership with Wago, then a separate CurseForge edition with
Overwolf's permission) is the reason D-002 keeps CurseForge optional.

What mrgl's application says, in short: a free, open-source (MIT) addon manager for Windows written in Rust,
one portable zip with no runtime, no installer and no server; the CurseForge source is one of several and
strictly optional, used only with the user's own key, within these terms; an author's
`allowModDistribution=false` is honored by opening the project page or taking a zip the user downloaded by
hand; the website is never scraped; no API data is cached; no ads, no monetization; the expected use is one
user's own AddOns folder (a few dozen addons, an update check a few times a day, a download only when an
update is installed). It names no other manager and makes no claim about one.

## The terms the source implementation follows

From the CurseForge 3rd Party API Terms and Conditions (the support article "CurseForge API"), as read on
2026-10-22; the clause numbers are the document's:

| Clause | The term | What mrgl does |
|---|---|---|
| 2.2 | the key is non-transferable and may not be disclosed to any third party | the key is the user's own, read from the environment or the config, never shipped in the zip, never printed (the doctor names it, present or absent) |
| 2.3 | Overwolf may set a quota at its discretion and may decline access beyond it; continued use past it may need a license with payment terms | one user, one AddOns folder; the update check asks once per addon and respects the answers' caching headers; no bulk or background polling |
| 3.1 | no product or service that competes with CurseForge or the Platform | mrgl manages a folder; it hosts nothing, lists nothing of its own, and sends the user to the project page |
| 3.1 (c), (d) | no decompiling, no circumventing security mechanisms | the API only, through its documented endpoints; the website is never scraped (D-002) |
| 3.1 (e) | no concealing of identity or location (no proxy or VPN to the API) | direct requests from the user's machine with the user's key |
| 3.1 (second e) | no saving or caching of data obtained through the API | the CurseForge source keeps no release list cache of its own (unlike the GitHub source); it asks again on every check and keeps only what the state sidecar needs to know what is installed (the installed file id and version, which are the user's own data) |
| `allowModDistribution` | an author may turn third-party distribution off; the API then returns no download URL | the source reports the addon as "distribution off": the window opens the project page, `add` takes a zip in hand (D-002) |
| 8, 9 | termination on material breach not cured in 14 days, or without cause for a specific app; on termination the key is deleted | a refused or revoked key turns the source off; the other sources are unaffected |

The terms grant Overwolf the right to name the developer (clause 11) and require no attribution from the
developer; mrgl names CurseForge as the source of an addon anyway, as it names GitHub, Wago and WoWInterface.

## The outcome

- 2026-10-22 — the application was submitted (task 007's Log has the date).
- 2026-10-29 — approved: CurseForge's e-mail ("Your CurseForge API Application - Approved") names the
  application `mrgl` and the 3rd Party CurseForge API, carries the personal API key and points to the Core
  API documentation; it attaches no term beyond the ones above, so the table stays the source's rule book.
  The key is the maintainer's own (clause 2.2: non-transferable): it lives in the Windows Credential Manager
  (`mrgl key set curse`, task 093), never in the repository, a release zip or a task file, and every user of
  mrgl applies for their own key the same way (D-002). The first requests against the real API are in task
  096's Verification: the game version type ids of `GET /v1/games/1/version-types` match the constants the
  source carried, and the manual round (install, update check, distribution-off project, adopt) passed.
