# 120 — A usage guide as HTML inside the release zip

## Context

The release zip carries a usage guide, `GUIDE.html`, one self-contained page generated from the README's user
sections (what it does, install, the window, the command line and its commands, the sources and the keys,
backups and sets, where the data lives) by a script under `scripts/` that `release.ps1` runs, in the voice of
the project and offline, no external asset; the README stays the source of the words.
Why: the M5 Trust roadmap line, and a user who unpacks the zip has no README next to the exes.
Done when: `release.ps1` packs `GUIDE.html` next to the exes, the page opens offline and reads as the README's
user half, a CI check keeps the generated page in step with the README, and the docs name the script.

Decided 2026-10-24: filed and started in one step from the roadmap's M5 line; the README stays the one source
of the user text, the page is generated, never hand-edited.

## Docs that move

- `docs/development.md`: the Layout bullet of `scripts/`, the release paragraph (what the zip holds), the
  sentence that says a usage guide is M5
- `README.md`: the Install section names the guide inside the zip; any README restructuring the generator
  needs (section markers) stays invisible to a reader
- `CONTRIBUTING.md`: the generated-page check in "Checks before a commit", if a check is added

## Not in this change

- Signed exes (103) and self-update (031)
- A guide for the window's every control (the page mirrors the README, no more)
- Screenshots or any binary asset

## Log

- 2026-10-24 — filed and promoted
- 2026-10-24 — `scripts/usage-guide.py`: the standard library only, one page with inline CSS, no script, no
  image, no external asset. The regions are picked by HTML comments in the README, invisible on GitHub:
  `<!-- guide: start -->` / `<!-- guide: end -->` around the intro, the example run, *What it will do* and
  *Install*, the command list with the prose after it, and *License*; `<!-- guide: section <title> -->` gives
  the long prose under *Build from source* (a heading the page leaves out) twelve headings of its own (*The
  command line*, *Sources*, *Adopting the addons you have*, … *Lists and the interface check*), so the table
  of contents has 14 entries. Markers rather than headings: the user text and the developer text share the
  *Build from source* section, and only markers cut it at the right line.
- 2026-10-24 — The header carries the voice table's banner line (`Mrglglgl.`), the version of `Cargo.toml`
  (read with the pattern `release.ps1` uses) and the regions' text before their first heading (the intro and
  the example run); a footer names the README and the repository. Markdown subset: `##`/`###` headings,
  paragraphs, `- ` lists with continuation lines, fenced code, code spans, links, `**bold**`, backslash
  escapes; a table, a quote, a numbered or nested list, emphasis, an image, raw HTML (any other comment
  included) or a level-1/4+ heading inside a region stops the script with the README line. The README has no
  table, so none is supported.
- 2026-10-24 — The page is generated at release time and never committed. A committed
  copy would have to be regenerated by every change that edits the README, and parallel task branches would
  meet in it as they meet in `CHANGELOG.md`; the release-time page has nothing to fall out of step. The check
  is therefore a dry run: `usage-guide.py --check` renders the page twice from the current README (the two
  renders must be byte-equal), validates markers, constructs and links, and writes nothing. It runs in the
  `lint` job after the changelog check (on tags too: nothing about a tag changes the page), in CONTRIBUTING's
  "Checks before a commit", and in `release.ps1` before the build, so a release fails fast.
- 2026-10-24 — Two rewrites fit the README to a page next to the exes: `target\release\` becomes `.\` (the
  command list reads `.\mrgl.exe …`, which works in the unpacked folder), and a link to a file of the repo
  points at that file in the release's tag (`<repo>/blob/v<version>/…`, `tree/` for a folder); a link to a
  file the repo lacks stops the script, an anchor the page has stays on the page.
- 2026-10-24 — The release notes footer (`changelog.py --notes`) names `GUIDE.html` among the zip's files.

## Deviations from the plan

- The README's command block under *Build from source* is split in two: `cargo build --release` alone in the
  first box, the command list from `target\release\mrgl.exe --version` on in the second, with the region
  markers between them. A marker inside a fenced block would be visible code, so the split is the one
  restructuring of the README a reader can see (two code boxes instead of one); the words are unchanged.
- Step 3 asked for a check that fails when the page is out of step with the README; with no committed copy
  (Log) the check is a dry run that fails when the README no longer renders.
- Step 4: no separate Python test file. The repo tests its scripts through their `--check` modes in CI
  (`changelog.py`, `sync-issues.py` have no unit tests), and `usage-guide.py --check` over the real README is
  that test; the error paths were exercised once by hand with synthetic READMEs (Verification).
- Step 5: this session opened no browser; the page's offline shape was checked in the file itself
  (Verification), opening it in a browser is the maintainer's look at the pull request.
